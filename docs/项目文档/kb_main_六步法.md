# 智能体搭建统一六步法（知识库文件）

> **这份文件的作用**：解决你当前最大的内容冲突 —— Demo 界面是 6 步、知识树 `t7-2` 是 7 步、知识树 `t4-3-4` 是 8 步，而且知识树内部"插件 vs 工作流"顺序自相矛盾。
> 本文件是**唯一权威版本**。上传到知识库主库，并在系统提示词里要求 Agent 只讲这一套。
> 版本：v1.0 ｜ 2026-09-10

---

## 一、为什么要统一

同一件事在你的产品里有三个答案，用户点"智能体搭建指引"看到的和问出来的对不上，信任会直接崩。

三处冲突的具体内容：

| 来源 | 步数 | 顺序问题 |
|---|---|---|
| Demo 界面 | 6 步 | 创建 → 提示词 → 知识库 → **插件** → **工作流** → 发布 |
| 知识树 `t7-2` | 7 步 | 创建 → 提示词 → 知识库 → **工作流** → **插件** → 调试 → 发布 |
| 知识树 `t4-3-4` | 8 步 | **选模型取 Key** → 提示词 → 知识库 → **工具** → **工作流** → 界面 → 测试 → 上线 |

**关键矛盾**：`t7-2` 说"先工作流后插件"，`t4-3-4` 说"先工具后工作流"。这个顺序**不能随便颠倒**——工作流里需要调用插件/工具节点，先设计工作流再补工具，通常要回头返工。

---

## 二、统一方案：一套骨架，两种详略

**原则**：面向"我要开始搭"的界面用 6 步；面向"深入讲解"的对话用 8 步。两者是同一套流程的粗粒度/细粒度视图，不矛盾。

### 界面展示版（6 步）

```
1 定场景      ← 新增，当前 Demo 缺失，也是最容易被跳过的一步
2 选模型
3 写提示词
4 配知识库
5 接工具并编排工作流   ← 合并，消除顺序争议
6 测试调优并发布
```

### 深入讲解版（8 步）

```
1 定场景
2 选模型，获取 API Key
3 写人设 Prompt
4 配知识库（RAG）
5 配工具调用
6 设计工作流
7 测试迭代（记录 BadCase）
8 部署上线
```

**映射关系**：6 步的第 5 步 = 8 步的第 5 + 6 步；6 步的第 6 步 = 8 步的第 7 + 8 步。

## 三、六步法逐条详解

### 第 1 步｜定场景

**在干什么**：想清楚这个智能体到底帮谁、解决什么事。

**产出物**：一句话场景描述 + 一个明确的"它能做/不能做"清单。

**什么算做对**：能用一句话说清"给谁用、解决什么、不解决什么"。例：
> "给工程项目的同事用，帮他们整理招投标资料、提取合同关键信息。不负责报价测算。"

**新手最容易错在哪**：
这一条是**新手放弃的头号原因**。绝大多数人一上来就想做工作流，跳过定场景，结果做出一个"能跑但没用"的东西，然后放弃。

**Agent 拦截话术**：
> "等一下，我先拦你一下。配工作流是第 6 步。如果场景没定清楚，工作流配得再漂亮也没用——你会做出一个能跑但没用的东西。先花 5 分钟告诉我你想让它干什么，就 5 分钟。"

---

### 第 2 步｜选模型

**在干什么**：选一个"大脑"，并拿到调用它的钥匙（API Key）。

**产出物**：确定的模型 + 一个可用的 API Key。

**什么算做对**：知道为什么选它（成本/能力/国内可访问性），不是随便挑的。

**选型参考**：

| 需求 | 建议方向 |
|---|---|
| 零基础第一次搭 | 用平台内置模型，先不折腾 API Key |
| 中文好、成本低 | 国内主流模型（豆包、DeepSeek、通义千问等） |
| 超长文档 | 长上下文能力强的模型 |
| 推理/逻辑任务 | 推理类模型 |
| 数据不能出内网 | 需开源可私有化部署的方案 |

**新手最容易错在哪**：一上来纠结"哪个模型最强"。**零基础阶段选哪个都能跑通**，先把流程走完比选对模型重要得多。

**参数提醒**：温度值（temperature）建议调低（0.3-0.6）。教学类智能体要的是稳定，不是创意。

---

### 第 3 步｜写提示词

**在干什么**：给智能体写"岗位说明书"。

**类比**：智能体是一个知识面很广但没上过岗的新员工。提示词就是告诉他：你是谁、干什么、怎么干、不能干什么。

**产出物**：一段系统提示词。

**必写的四块**：

| 块 | 内容 | 例子 |
|---|---|---|
| 角色 | 它是谁 | "你是 XX 领域的资深顾问" |
| 任务 | 它要干什么 | "帮用户判断合同里的风险条款" |
| 边界 | 什么不能干 | "不确定的条款要标注'需人工核实'，不要猜" |
| 格式 | 怎么输出 | "先给结论，再列风险点，最后给建议" |

**什么算做对**：把提示词给一个陌生人看，他能准确说出这个智能体会怎么回答。

**新手最容易错在哪**：
1. 只写"你是XX助手"就完事 —— 任务和边界全缺，智能体会自由发挥
2. 写了一大堆但没写"不能做什么" —— **边界比能力更重要**，尤其在需要准确的场景
3. 一次改十个地方 —— 改完不知道是哪个改动起了作用。**一次只改一个变量**

**优化闭环**：发现问题 → 改一处 → 重测 → 记录是否变好。这是提示词工程的本质，不是玄学。

---

### 第 4 步｜配知识库（RAG）

**在干什么**：给智能体配一本"随时能翻的参考手册"。

**类比**：新员工光有岗位说明书还不够，还得给他公司的手册。遇到问题先翻手册，而不是凭记忆瞎说。

**产出物**：一个已上传并关联到智能体的知识库。

**什么算做对**：问一个只有你资料里才有的问题，智能体能答出来并引用依据。

**RAG 的运行逻辑（一句话）**：
> 用户提问 → 先去知识库搜相关内容 → 把「搜到的资料 + 用户问题」一起给大模型 → 大模型基于资料生成答案。

**为什么需要它**：大模型有三个天生短板——会胡说（幻觉）、不知道你的内部数据、知识有截止日期。RAG 是目前解决这三个问题最主流的方案。

**新手最容易错在哪**：
1. **文档切得太碎**：切片把一句话切断了，检索出来的片段没有上下文，答非所问
2. **什么都往里塞**：知识库塞了不相关内容，检索时把真正有用的挤下去
3. **指望它万能**：RAG 解决"不知道你的资料"，不解决"模型本身能力不够"

**什么时候不用 RAG**：如果问题是通用知识（模型本来就会），配知识库反而增加成本和不稳定。

---

### 第 5 步｜接工具并编排工作流

**在干什么**：
- **接工具**：让智能体能"动手"——读 PDF、查网页、算数、生成图片、连企业系统
- **编排工作流**：把多步骤任务串成固定流程，像流水线

**类比**：
- 工具 = 给它配的办公软件（它有脑子，但需要手和脚）
- 工作流 = 标准作业流程 SOP（多步骤任务的固定走法）

**产出物**：能自主完成一个多步骤任务的工作流。

**什么算做对**：给它一个真实任务，它能按预期步骤跑完并输出正确结果。

**运行逻辑**：按节点顺序执行，上一个节点的输出是下一个节点的输入。每个节点可以是大模型、工具、代码，甚至人工审核。

**为什么把这两步合并讲**：工作流里需要调用工具节点。先设计工作流再补工具，通常要回头返工。**先明确需要哪些工具，再编排流程**。

**新手最容易错在哪**：
1. **一上来就玩工作流**（回到第 1 步的坑）
2. **多智能体过早引入**：一个智能体能做好的事，用三个智能体协作，复杂度爆炸
3. **节点太多导致调试困难**：一个 15 个节点的工作流，出错时你不知道是哪个节点。**先用 3 个节点跑通，再加**

---

### 第 6 步｜测试调优并发布

**在干什么**：测出问题、修掉、再上线。

**产出物**：一份测试记录（BadCase 清单）+ 一个已发布的智能体。

**什么算做对**：准备了 5-10 个真实测试用例，逐个跑过，记录所有失败情况。

**核心概念——BadCase**：
BadCase 就是"智能体输出出错、效果不达标、任务执行失败"的具体案例。**收集并逐个修复 BadCase，是 AI 产品经理的核心工作之一**，不是开发的事。

**迭代循环**：
```
发现问题 → 分析原因（是提示词？知识库？工具？模型？）
→ 改一处 → 回归测试 → 确认变好 → 下一个
```

**准确率从 70% → 80% → 90% 就是迭代的价值。**

**排查问题看什么**：Trace（链路追踪）—— 一次任务的完整流水：用户输入 → 怎么拆解的 → 调了哪个工具 → 工具返回什么 → 哪一步报错 → 最终输出。这是定位问题的依据。

**新手最容易错在哪**：
1. **只测"正常情况"**：一定要测边界和异常（空输入、超长输入、无关问题、恶意输入）
2. **改完不回归**：修了 A 场景，B 场景坏了。每次改完必须重跑全部用例
3. **不记录**：同一个错犯三次，因为没记下来

## 四、发布渠道与上线后

**发布方式**（以平台实际能力为准，不要凭记忆回答用户）：
- 平台内发布，生成分享链接
- 发布到网页 / 微信 / API 等渠道
- 自定义网页部署（如需自定义界面）

**上线后要做的事**：
1. 收集真实用户反馈
2. 监控使用数据
3. 持续收集新的 BadCase
4. 按"先修信任、再修准确、最后修体验"的顺序迭代

---

## 五、给 Agent 的回答规则（写进系统提示词）

回答智能体搭建类问题时：

1. **只用本文件的六步/八步**，不要自创版本
2. 先确认用户卡在第几步，再讲那一步
3. 每步都讲清：干什么 / 产出什么 / 什么算做对 / 最容易错在哪
4. 发现用户跳步（尤其跳过第 1 步），用第 1 步的拦截话术拦一下
5. 涉及平台具体功能（支持什么格式、免费额度、发布渠道）**绝不凭记忆回答**，让用户去后台核实

## 六、FAQ（预置常见问题）

**Q：一定要用 API Key 吗？**
A：不一定。平台的零代码模式可以直接用内置模型。API Key 是在需要外部调用、或者要对比不同模型时才需要。零基础第一次搭，建议先用内置模型跑通。

**Q：RAG 和微调该选哪个？**
A：**先试 RAG。** RAG 成本低、见效快、改资料就能更新。微调成本高、周期长，只有对回答风格或专业度要求极高时才考虑。绝大多数场景 RAG 就够了。

**Q：为什么我的智能体答得不准？**
A：按这个顺序查：① 提示词写清楚了没（90% 的问题在这）→ ② 知识库里有没有对应内容 → ③ 切片有没有切断语义 → ④ 模型选得合不合适。**不要一上来就想着换模型或上微调。**

**Q：工作流和智能体什么关系？**
A：智能体是"会思考的人"，工作流是"给他定的作业流程"。简单任务不需要工作流，多步骤、要固定顺序的任务才需要。

**Q：搭一个要多久？**
A：跑通一个能用的，第一次大概 2-4 小时。做到好用需要反复测试迭代，通常几天到几周。**别信"10 分钟搭一个"的说法**，那只是点完按钮，不是能用。
