## 一、设计主线：一个"工作台"，不是"问答机器人"

这是最重要的一条产品判断。

| | 问答机器人 | 工作台 |
|---|---|---|
| 用户带着什么来 | 具体问题 | 模糊焦虑 |
| 交互形态 | 一问一答，答完结束 | 有状态、有进度、有下一步 |
| 用户离开时 | 得到一个答案 | 得到一个"待办" |
| 回来的理由 | 又遇到问题 | 上次的任务没做完 |
| 对应你的痛点 | 只能解决"某句话不懂" | 解决"不知道从哪开始" |

**你的用户是零基础转行人群，他们的第一状态不是"我有个问题"，而是"我很慌，不知道从哪下手"。**

所以工作台的核心不是"答得准"，而是**"让用户每次离开时都知道下一步做什么"**。

## 二、功能模块清单

### 模块 0｜分诊台（入口，最高优先级）

**解决**：用户进来不知道问什么
**做什么**：用 2 个问题把用户分流到对应路径，并给出一个明确的起点
**产出**：一句定位 + 一个起点任务

诊断维度（**只问 2 个，不要问 3 个以上**，多了用户会跑）：

| 维度 | 问法 | 用途 |
|---|---|---|
| 起点 | "你现在做什么工作？之前接触过产品或技术吗？" | 决定要不要补基础概念 |
| 目标 | "你是想先搞懂 AI 产品怎么运转，还是想先搭一个智能体出来？" | **决定走 A 线还是 B 线** |

> 时间投入、专业细分这些放到后面再问。
> **入口处每多问一个问题，流失率就上一档。**

---

### 模块 1｜主线 A：AI 产品 0→1 全流程（对应痛点①）

**解决**：搞不懂 AI 产品从 0 到 1 的完整运行逻辑
**做什么**：给用户一张"地图"，然后带着他一段一段走

**内容骨架（九个阶段）**：

```
1 机会识别 → 2 场景判断 → 3 需求定义 → 4 原型验证 →
5 技术选型 → 6 开发迭代 → 7 上线 → 8 数据回归 → 9 商业化
```

**每个阶段必须回答四个问题**（这是模块的关键设计）：

| 问题 | 为什么重要 |
|---|---|
| 这个阶段在干什么？ | 零基础用户不知道"原型验证"是什么 |
| 你要产出什么？ | 给他一个可见的成果物，有掌控感 |
| 什么算做对了？ | 判断标准，否则他不知道自己做得好不好 |
| 新手最容易在哪翻车？ | 避坑比学方法更有用 |

**交互方式**：
- 用户说"我想了解 AI 产品怎么做" → **不要一次讲九个阶段**，先给地图全貌（一张表），然后问"想从哪一段开始？"
- 每讲完一个阶段 → 给一个该阶段的**练手任务**（例如："拿你熟悉的行业，写 3 个可能用 AI 解决的场景"）
- 用户提交练手结果 → 给反馈，然后进入下一阶段

**关键设计：AI 可行性与传统产品差异要单独成模块**
因为这是 AI 产品经理区别于传统 PM 的核心，也是最容易被零基础用户忽略的：
- 不确定性管理（AI 会答错，产品怎么兜）
- 数据驱动迭代（不是靠直觉改版）
- 能力渐进释放（模型升级了，产品能顺势变强）

### 模块 2｜主线 B：智能体搭建六步法（对应痛点②）

> ⚠️ **本模块已统一，权威内容见 `kb_main_六步法.md`**
>
> 统一方案：**界面展示用 6 步，深入讲解用 8 步**（同一流程的两种详略）。
> 你原有三处冲突（Demo 6 步 / 知识树 `t7-2` 7 步 / 知识树 `t4-3-4` 8 步）
> 以及"插件 vs 工作流"的顺序矛盾，已在 `07_资产对齐与整合诊断.md` 4.1 节说明并处理。

**解决**：想搭智能体，但不理解底层逻辑和完整流程
**做什么**：把"搭智能体"拆成能动手的步骤，逐步引导完成

**界面展示版（6 步）**：
```
1 定场景 → 2 选模型 → 3 写提示词 → 4 配知识库
→ 5 接工具并编排工作流 → 6 测试调优并发布
```

**深入讲解版（8 步）**：
```
1 定场景 → 2 选模型取 API Key → 3 写人设 Prompt → 4 配知识库 RAG
→ 5 配工具调用 → 6 设计工作流 → 7 测试迭代（记 BadCase） → 8 部署上线
```

**第 1 步「定场景」是新增的，也是最重要的一步。** 你的 Demo 当前没有这一步，
而它恰恰是零基础用户放弃的头号原因——跳过它直接玩工作流，会做出"能跑但没用"的东西。

**交互方式（这是模块设计的重点）**：

不要"讲完六步让他自己搭"，而是**带他搭一个真的出来**。

- 每步讲完 → 立刻让他在平台上做一次
- 他做完回来说结果 → 诊断 → 进下一步
- 全程围绕**一个他自己选的场景**（比如"帮我搭个帮我看简历的助手"）

**必须显式打断的错误路径**：

| 用户行为 | 为什么要拦 |
|---|---|
| 直接问"工作流怎么配" | 配工作流是第 6 步。没定场景就配工作流 = 白做 |
| 直接问"怎么让回答更准" | 90% 的情况是提示词没写好，不是该上 RAG |
| 一上来就想接很多工具 | 复杂度失控，先跑通最小闭环 |

**"底层逻辑"怎么讲（零基础版类比）**：

| 概念 | 类比 | 一句话解释 |
|---|---|---|
| 大模型 | 一个知识面很广但没上过岗的新员工 | 什么都知道一点，但不知道你的业务规矩 |
| 提示词 | 岗位说明书 | 告诉它你是谁、干什么、怎么干 |
| 知识库 | 给它配的参考手册 | 让它答得有依据，不瞎编 |
| 工具 / 插件 | 给它配的办公软件 | 让它能查天气、能算数、能搜索 |
| 工作流 | 标准作业流程 SOP | 多步骤任务的固定走法 |
| 微调 | 送它去专项培训 | 成本高，通常是最后才考虑的手段 |

> 这张表建议直接放进扣子的知识库，让 Agent 能稳定复述。

### 模块 3｜伴随模块：进度与回访（工作台之所以是"台"）

**解决**：用户答完就忘、学完就断
**做什么**：
- 记录用户当前在 A 线第几阶段 / B 线第几步
- 每次开场先接上次进度："上次你卡在需求定义，我们接着来？"
- 给用户一个"未完成的下一步"

**这是把"问答"变成"工作台"的关键模块**，也是最容易被忽略的。
如果扣子不支持状态存储，就用**对话内的轻量方式**替代：
让 Agent 在每次回答结尾标准化输出「你的进度：A线 3/9 · 下一步：把需求写成一句话」，用户在对话里就能看到自己的位置。

---

### 模块 4｜书目导航（你现有知识库的正确位置）

**解决**：用户想读书但不知道读哪本
**做什么**：基于现有 13 本书的资料，回答"该读什么"
**定位**：这是**辅助模块，不是主体**

必须显式告诉用户这个模块的能力边界：

> "我能帮你**选书**、判断哪本适合你现在的阶段。
> 但'具体怎么做'这类问题，书单资料里只有章标题，
> 我会用产品经验给你框架，你需要注意区分。"

**这个诚实的边界说明，比假装什么都能答更能建立信任。**

---

### 模块 5｜术语翻译器（零基础用户的隐形刚需）

**解决**：用户看到"RAG""微调""Token"就懵
**做什么**：任何时候用户问"XX 是什么意思"，用统一格式回答

固定格式：
```
一句话解释（≤20字）
+ 生活化类比
+ 它在你做产品时对应什么事
+ 你现在需不需要懂它（大多数：不需要深究）
```

**最后一条特别重要**。零基础用户最大的焦虑来源是"我是不是什么都得学"。
主动告诉他"这个概念你现在不用深究"，本身就是价值。

## 三、交互流程

### 3.1 首次进入

```
用户进入
   ↓
欢迎语 + 3 个快捷入口（见 04_欢迎语与引导话术.md）
   ↓
用户点任一入口 / 或自由提问
   ↓
【分诊台】问 2 个问题（起点、目标）
   ↓
给出定位 + 起点任务
   ↓
进入对应主线
```

### 3.2 主线 A 循环（AI 产品 0→1）

```
给出产品 0→1 五阶段地图（用户调研 → 需求分析 → 方案设计 → 测试迭代 → 上线发布）
   ↓
用户选一个阶段（或从第 1 段开始）
   ↓
讲清：干什么 / 产出什么 / 什么算对 / 常见坑
   ↓
给一个练手任务
   ↓
用户做完反馈 → 诊断 → 修正
   ↓
标准化输出进度 → 下一阶段
   ↺
```

### 3.3 主线 B 循环（智能体搭建）

```
确认场景（用户自己的真实需求）
   ↓
第 N 步：讲原理 → 给操作 → 让他现场做
   ↓
用户说结果 → 诊断问题
   ├── 做对了 → 下一步
   └── 做错了 → 定位是哪一步的问题（不一定是当前步）
   ↓
标准化输出进度
   ↺ 直到六步跑通，得到一个能用的智能体
```

### 3.4 每次回答的固定结构（由系统提示词强制）

```
① 一句话结论
② 打个比方
③ 步骤 / 清单
④ 今天就能做的一件事
⑤ 一个追问
────────────────
📌 你的进度：A线 4/9 · 下一步：写一版需求假设
```

第 ⑤ 项和第 ⑥ 项（进度条）是**让用户"被推着走"的机制**，不是装饰。
